# Changelog

All notable changes to Construct are recorded here. The format follows
[Keep a Changelog](https://keepachangelog.com/en/1.1.0/). The version policy is
in [docs/VERSIONING.md](docs/VERSIONING.md). Numbers in brackets are pull
request or issue numbers.

## [Unreleased]

### Added
- `parseJsxTree` node records carry `content`: the element's immediate text and `{expression}` children, in source order, `{kind: 'text'|'expression', value, start, end}[]` (#697, part of #685). A consumer that needs every piece of visible text on a page (Trace's dynamic-text marking) no longer needs a second parser. Additive: existing fields (`start`/`end`/`line`/`column`/`children`/...) are unchanged. Whitespace-only text is skipped (documented choice: it is almost always indentation, not visible content); an empty `{/* comment */}` container is skipped too. `value` always equals `source.slice(start, end)` for both kinds (the expression kind's span excludes the surrounding `{`/`}`, matching `jsxAttributes`' `'expression'`-kind convention).
- A traceability report from requirement sentence to function to generated file, and back (#673, R5 of #576, part of #570): `construct research spec <file> --coverage [--feature <name>] [--format json|text]` lists, per sentence, its status (`covered`, `out-of-scope` with the spec's reason, or `uncovered`), the functions and the states, events and transitions that claim it, and the files `--generate` writes for them (the generator's own paths: `plannedSpecFiles` in `specToCode.mjs`, which `generateFromSpec` now calls, pinned by a test that compares them with what `--generate` writes); then each function with the sentences it cites or `orphan` when none of its `req` links resolves (unknown links listed), then each generated file with the sentences it serves. `--format json` is a fixed shape (`construct.machine-spec-coverage.v1`, ids are the spec's own). Exit 1 only when a sentence is uncovered and not out of scope; it also runs on a spec whose only violations are `SPEC-009`/`SPEC-010`, any other violation prints the plain validation report; exclusive with `--generate` and `--read-back`. No model. New `packages/core/research/coverage.mjs` (`coverageOfMachineSpec`, `renderCoverage`, `uncoveredSentences`, `COVERAGE_SCHEMA`); the worked example and a fixture with a gap are pinned by `test/machineSpecCoverage.test.mjs` against `fixtures/machine-spec-coverage/`; docs in `docs/machine-spec.md`.
- A machine-spec read back to you in plain English (#672, R4 of #576, part of #570): `construct research spec <file> --read-back [--format json|text]` prints, per requirement sentence, the sentence and the states, events, transitions and functions whose `req` points at it, each in plain words in the workflow narrator's own wording (`narrateMachine` for the summary, `transitionSentence` for every transition, so a guarded branch and its "Otherwise" fallback read as in `research workflow`); a sentence out of scope is listed with its reason, an item claiming several sentences shows under each, the declared types come last, nothing is dropped. `--format json` is the same as a fixed-shape list (`construct.machine-spec-readback.v1`, ids are the spec's own). A spec that fails a `SPEC-*` check prints the validation report and reads nothing back; exclusive with `--generate`. No model. New `packages/core/research/readBack.mjs` (`readBackMachineSpec`, `renderReadBack`, `READ_BACK_SCHEMA`); the worked example's output is pinned by `test/machineSpecReadBack.test.mjs` against `fixtures/machine-spec-readback/`; docs in `docs/machine-spec.md`.
- An English requirement becomes a checked function breakdown, with no model in the path (#576, part of #570; slices #584 and #593): `construct research spec <file> [--format json]` checks a `machine-spec.v1` (states, events, guarded transitions, typed functions with a precondition and postcondition, every item traced to its sentence by `req`; JSON Schema in `packages/core/research/`, worked example beside it) and refuses it with a stable `SPEC-*` code, the path and the reason: an unreachable state, an unknown state or event, an untyped function, a sentence neither covered nor marked out of scope, and now (`SPEC-013`, `SPEC-014`) a type string that does not parse or names a type nothing declares (a new optional `types[]` declares them, e.g. `Session`). `--generate [--feature f]` on an accepted spec writes, in one command, the XState workflow with its typed state union, event payloads typed into the event union, named guard stubs, the declared types in the feature's `types.ts`, one `defineService` stub per function and the machine's locked every-path unit test (`generate tests --unit`, declaring the `frozen:`/`nonLayer:` test regions once); the result passes `construct validate` and `tsc --strict` and the test runs, all three checked in `test/specToCode.test.mjs`. `compileWorkflow` now emits `context: {}` for a machine with no context (XState's config type requires the key, so every no-context machine failed `tsc` before) and accepts `eventPayloads` and `typeImports`. Not built: drafting the spec from English with `--llm` and the check-and-retry loop (R3), the read-back diff (R4), the Cockpit screen (R6). `docs/machine-spec.md`.
- Every layer rejects stale input the way a state machine does (#577, part of #570; slices #586, #594, #590 shipped earlier, the rest of the proposed rows here as #667, #668, #669): three more opt-in rules, off by default, each with a bad and a good fixture under `fixtures/staleness/` and a `node --test` file. `CONTROLLER-003` (opt in with `rules: { CONTROLLER-003: warning }`) flags a controller that calls `useState`, `useReducer`, `useRef`, `useEffect`, `useLayoutEffect`, `useMemo` or `useCallback`, so it can only bind the hook's live value, never a copy from an earlier render. `HOOK-003` flags a `useEffect`/`useLayoutEffect` in a hook that starts `addEventListener`, `setInterval`, `setTimeout`, `subscribe`, `.on(`, `new AbortController`/`WebSocket`/an observer and returns no cleanup. `ROUTE-003` flags a route that reads `params`/`searchParams` (`params.id`, `searchParams.get(...)`, `await params` destructuring, `useParams()` destructuring) instead of forwarding them whole. Each violation carries file:line, a why and a concrete `suggestedFix`. The Hook, Controller and Route rows of `docs/staleness-by-layer.md` now read ENFORCED (opt-in) with `path:line`, and its stale note about the optional Pages-editor hash is replaced by the shipped `HASH_REQUIRED` guard (#590). Run over `ui/client`, `example/`, `fixtures/` and `site/`: 2 of 158 hook files are reported (one is the bad fixture; `useFaviconMotion.tsx` stops its timer in a sibling effect, a documented exception), 11 of 64 controllers hold state, 1 of 26 route files reads params (the bad fixture). No LLM.
- A warning when state is a bag of flags (#573, part of #570; slices #581 and #592): `STATE-001` (off by default, opt in with `rules: { STATE-001: warning }`) reads the state shapes of workflow and hook files (interface, object type alias, `useState`/`useReducer` initial object or type argument, initial-state const, XState `context`) with the AST and flags two or more status flags (`isLoading` + `isError`, `pending` + `failed`) or one flag next to both an `error` and a `data`-style field, with file:line, the offending fields and a concrete `status` union rewrite built from the real field names and types. New with #592: a result slot named after its domain (`listing: Listing | null`, `session?: Session`) now counts as the data field beside a flag and an error (never a primitive or key such as `notice: string | null` or `selectedId`, never an untyped `null`). Checked with no false positive on `ui/client` (192 workflow and hook files: the 2 hits, `AuthSession.ts` and `DirectoryBrowser.tsx`, are real bags of flags), `example/` (6 files) and `fixtures/` (34 files: 0 hits); the README example and every suggested union are compiled by a test. No LLM.
- `construct create service --openapi` writes the spec's response schemas as Zod, ready to hand to `defineService({ schema })` (#575, part of #570; completes the story after #585). The same hey-api (MIT) that writes `types.gen.ts` runs its `zod` plugin, so `features/<feature>/services/<name>/zod.gen.ts` holds one `z<OperationId>Response` per operation (`$ref`, `allOf` and the rest resolved by hey-api, not by Construct): `defineService('listPets', fn, { schema: zListPetsResponse })` then returns `{ status: 'ok', value }` typed from the spec or `{ status: 'error', kind: 'schema', issues }`, never a throw. Off unless asked: the file is written when the project's package.json declares `zod` (dependencies, devDependencies or peerDependencies) or with `--schema`; `--no-schema` never writes it; otherwise the command prints one line saying zod is not in package.json, so a project without zod keeps compiling and its output is byte-for-byte what it was. A spec with no response schema (only 204s, say) writes none. In core, `generateServiceFromSpec(root, name, feature, spec, { schema: true | false | 'auto' })`, `zodDeclared`, `resolveSchemaEmit`; the file is appended to the returned list. Tests: the five-file and four-file outputs, the `auto` rule, the no-response spec, the CLI messages, and a real `tsc` plus real zod run of a `defineService` consumer of the generated schema. Left out: the `create.service.openapi` plan flow does not pass `--schema` (it follows the project's zod rule), request-body and path-parameter schemas are written by hey-api into the same file but nothing checks them yet, and generating the `defineService` wrapper itself (the RTKQ endpoint file is unchanged). zod 4 only (hey-api's default).
- Every path of a workflow, checked with no browser (#574 via #583, part of #570): `construct generate tests --unit <feature> [--dry-run] [--prune]` writes one LOCKED node test per workflow machine, `features/<feature>/tests/generated/<machine>--every-path.test.ts`, with the same marker, `frozen:`/`nonLayer:` regions, overwrite refusals and prune rules as the Playwright specs, and it complements them (a spec drives the UI through one scenario, this walks the whole state space in milliseconds; `*.test.ts` is node's, `*.spec.ts` stays Playwright's). The file walks the machine with `@xstate/graph` (MIT): `getShortestPaths` reaches every state, `getAdjacencyMap` visits every transition, both compared with a table baked in at generation time and read statically from the machine (`STATES`, `REACHABLE`, `TRANSITIONS`: per resting state and user event, the states the flow may land on, several for a guarded group, a transient `always` state or a final child's parent `onDone`). A transition removed, retargeted or added fails with a one-line reason (`failed --RETRY--> is gone (it landed on loading)`); `construct generate tests --unit <feature>` refreshes the table once the change is intended. Run under the project's own runner with `tsx --test` (the machine files are `.tsx`); `construct init` scaffolds `@xstate/graph`, `tsx`, `@types/node` and a `test:unit` script, and the command prints the `npm install -D ...` line when they are missing. Machines that are not an exported `const`, or that use `parallel`/`history` states, are skipped with the reason. Core: `generateUnitTests`, `planUnitTests`, `pathModel` in `packages/engine/testUnitGenerator.mjs`. See `docs/GENERATED_TESTS.md`, "Every path, no browser". Left out: a Cockpit button for it, parallel and history states, checking guard conditions or service outcomes (those need a fixture).
- How a list, detail or dashboard screen shows its loading, empty (or not-found) and error states is one closed question, `q-states` (#622, part of #616, builds on the typed state unions of #570): `default` (first: a message for each state from one notice component, what these screens always had), `custom` (a component of your own for each state: `<Name>Loading`, `<Name>Empty` or `<Name>NotFound`, `<Name>Failed`, starting with the same text and role), `skip-empty` (no view for the empty or not-found state; list and detail) or `skip-all` (no view for any state), with stable ids, the rules' suggestion and a reason, offered beside the data source and asked only for shapes that fetch (`statesOffer`, `STATES_TABLE` in `packages/core/shape-states.mjs`). It is carried through `planFromBlocks` as `--states` on every unit and on the proof (left out for `default`, so an old plan is unchanged), through `construct create layer|<layer>|proof --states`, MCP `placement_place` and `POST /api/requirement/read` (answered by id, attributed, recorded as the decision trace `requirement.plan.states`), and drawn on the Requirement screen as a **Screen states** card with a plain line about what a state is. A skip is a warning (`warnings` of the plan, shown beside Approve, never a block) and removes a view, never a state: the typed union is unchanged. The proof follows the choice: a skipped state is asserted to show nothing (a screen that shows it fails the proof naming the state), and the browser flow keeps the flow of every state with a view. A wrong option is a typed plan error (`PLAN_STATES_UNAVAILABLE`). `docs/PLACEMENT.md`, "How a screen shows its states".
- A local embedding classifier proposes options behind the decision seam, scored by replay (#645, part of #616, depends on #647): a new model kind, `prototypes.json` (`construct.prototypes-model.v1`), for each closed question the example words per option (the words people chose on the TRAIN split plus an optional curated seed, at most 100 per option and 5000 in all), and a fixed, dependency-free embedding, `embed.v1` (signed hashing of the 2-, 3- and 4-grams of the word, divided by its length, 256 numbers; `packages/core/decision-prototypes.mjs`, export `@line/construct-core/decision-prototypes`). The provider embeds the quoted word of the question, takes for each ENABLED option the cosine similarity of its closest example, and suggests the best with the similarity as `score`, the runner-up and a one-line reason (`closest example "customers" (100% similar): entity`), or answers `null` under `minScore`, when two options are closer than `minMargin`, for a question it has no examples for or that quotes no word. No LLM call, no download, no runtime; about 5 ms to load and 0.04 ms per suggestion. `construct model import` now loads and replays a `prototypes` bundle on the held-out records against the rules baseline (a bad one is `MODEL_PROTOTYPES_INVALID`), it registers DISABLED, `construct model enable` accepts it, and the project plugin file of #647 serves it; only a verified, hash-checked registry copy is ever read. New `construct traces replay --model <name> [--all]` scores a registered model offline, enabled or not, on the records it has not seen (the held-out ones of its export and everything recorded after it; `--all` includes the ones it was built from). The kit gains `train-kit/build_prototypes.py` (standard library, repeats `embed.v1`, `--seed` for curated words, `TRAIN_KIND=prototypes ./train.sh`), a golden bundle and tests on both sides that pin the same embedding. Left out on purpose: a neural embedding (potion-base-8M, bge-small, MiniLM) and an ONNX loader (a versioned `embedder` lets `embed.v2` arrive later, replay-earned), SetFit tuning and an instruction-model chooser. No dependency was added; `docs/TRAIN-ELSEWHERE.md`, section 3b.
- The decision model is trained on ANOTHER machine and comes back as verified data (#647, part of #616); nothing trains on the dev machine. `construct traces export --out <dir> [--since <date>] [--chooser <id>] [--yes]` PREVIEWS first (records per chooser, the fields, the date range, the project key hashed, and that no path or secret is in it; writes nothing, not even a ledger) and with `--yes` writes a dataset bundle: `dataset.jsonl` (each record re-validated with `validateTrace`; a failing one is dropped and counted, never repaired; a deterministic 80/10/10 train/validation/test split by a hash of the record id), `schema.json`, `manifest.json` (counts, sha256 of every file, the dataset hash, Construct version, providers seen, chooser ids, the split rule, the creation time supplied by the caller) and `README.md`, byte-for-byte the same for the same inputs and clock. A project with `traces: off` contributes nothing; the folder may not be inside the project or a link; each export is recorded in a ledger in the state directory (dataset hash and the held-out test ids). New `construct model import <dir> [--yes]`: verifies a model bundle as PLAIN DATA (only `manifest.json`, `checksums.txt`, `eval-report.json`, `MODEL_CARD.md`, `features.json`, `prototypes.json`, `model.onnx`; no script, pickle, executable, link, sub-folder or path; size caps; sha256 of every file; schema versions; a dataset hash THIS project exported), nothing in it is ever executed, then replays the held-out test records against the rules baseline (the yardstick of `traces replay`) with the JSON structured-feature classifier (`features.json`: logistic-regression weights over features of the question as offered, scored in pure JavaScript; an `.onnx` or `prototypes.json` bundle is verified and stored, not loaded) and, with `--yes`, registers the model DISABLED in the state directory (`architecture.yml` is never edited); `construct model list|remove|enable|disable`; a project plugin file `export default registeredModelProvider('<name>', { root })` uses an ENABLED model and falls back to the rules provider when it is disabled, missing or altered. Every failure is a typed code (`MODEL_FILE_NOT_ALLOWED`, `MODEL_CHECKSUM_MISMATCH`, `MODEL_DATASET_UNKNOWN`, ...), exit code 1 (2 for usage), never a stack trace. The training kit is the folder `train-kit/` (not part of any package, no dependency on Construct, standard-library Python): `train.sh <dataset> <out>` and `train.sh --watch <inbox> <outbox>` (new dataset hashes only, `nice`, a hard time limit, a memory guard of 8 GB free, a heartbeat file), `train_features.py`, a launchd template `com.line.train.plist` for the training MacBook, notes for age-encrypted transport, a fixture dataset with a golden model and its own test. A test asserts that core, cli, engine and mcp import no training dependency and have no `train` verb. New exports `@line/construct-core/decision-dataset`, `/decision-features`, `/decision-model-bundle` and `/decision-model-registry`. Left out: embedding prototypes, an ONNX loader, LoRA/MLX, installing the launchd service, decrypting inside the kit. See docs/TRAIN-ELSEWHERE.md and train-kit/README.md.
- The Requirement screen offers every plan question and proves each shape in a browser (#659, part of #616). - Next.js route handler (#625, part of #616; its other half, add a dependency, is `add.dependency`, #654): `construct create handler <Name> --feature f --method GET|POST|PUT|DELETE --path /api/<x> [--service Name] [--entity E] [--fields ...] [--format json]` (the new `create.handler` flow in `PLAN_FLOWS`, mirrored in `schemas/plan.v1.json`, derived touches, usage) writes `app/api/<x>/route.ts`: the exported method hands the request to the service and answers with the status its typed result maps to (`ApiResult`: ready 200, invalid 400, not-allowed 405, error 500, decided in a domain unit `to<Name>Http`, never in the route: no `if` and no business logic, so ROUTE-001 and ROUTE-002 stay whole), every other method of the four is a typed JSON 405 with an `Allow` header, and the route never reads a secret (the service does). Without `--service` a typed in-memory service (`serve<Name>`: GET lists rows, POST validates and adds one, PUT replaces one by id, DELETE removes one by `?id=`) is written; with `--service <Name>` the handler delegates to that service's first `defineService` unit. The feature's `types.ts` gains `ApiResult` and `ApiReply` (and the entity), and the locked proof (`<Name>Api.proof.test.ts`) shows the status of every typed result, a typed 405 for every other method and, for a generated service, a good and a bad request, failing with `POST: the 405 state is wrong, it reaches 200.`-style messages. A react-spa project is refused with `A route handler needs a Next.js project`; an existing route file with other content, a service that is not there and a type that means something else are refused with the reason and nothing is written; idempotent. In the Requirement chain the closed question `q-handler` (`add-handler | skip`, add first) is raised on a Next.js project when a shaped list, form or wizard screen reads its `endpoint` source and no route file answers that path, adds the `create.handler` step and its proof step, is a decision trace (`requirement.plan.handler`), is accepted by MCP `placement_place` and the Requirement API, and is drawn by the Cockpit as a **Route handler** card. Left out: dynamic segments (`[id]`), several methods in one route file, a detail or dashboard screen's endpoint, a database, `middleware.ts`.

Left out: wiring a store into a screen, persistence, a shared provider around it, derived values.
- Route guard (#629, part of #616): choose who may open a screen from a closed list, as a deterministic block with no model. `construct create guard <Name> --feature f --access public|signed-in|role [--roles a,b] [--redirect /sign-in] [--route /r] [--format json]` (the new `guard.route` flow in `PLAN_FLOWS`, mirrored in `schemas/plan.v1.json`, derived touches, usage) writes a small typed slice of the feature: a pure access decision (`decide<Name>Access`, `defineDomain`: allowed, signed-out or wrong-role), a session hook that is SIGNED OUT until a provider above the screen supplies a session (or, when the project already has a session provider whose value is a `Session`, a hook that reads it), a fallback notice (`role="alert"`, with a link to `--redirect` when given), an expression that shows what it wraps only when access is allowed, and a guard controller; it edits the route entry to render `<XGuardController><XController /></XGuardController>` (Next.js `app/<route>/page.tsx`, react-spa `src/App.tsx`), so the screen is a child that is never rendered, and its data hooks never run, for a person who is not allowed. `public` writes nothing and says so. Idempotent (a second run changes nothing), refuses with the reason and writes nothing (no route renders the controller, the screen is already guarded by another rule, a `Session` or `Access` type that means something else). The proof (`<Name>Guard.proof.test.ts`, locked, run by `construct test proof`) renders signed-out, wrong-role and allowed and fails naming who was let in or kept out. In the Requirement chain the closed question `q-access` (`public | signed-in | role`, default first: `role` when the card names a role such as "admin", `signed-in` when it has a session noun such as "logged-in user", else `public`) adds the guard step and its proof step to a wired shaped plan, is a decision trace (`requirement.plan.access`), is accepted by MCP `placement_place` and the Requirement API, and is drawn by the Cockpit as an **Access** card. Left out: an auth provider integration, `middleware.ts`, a real redirect (the fallback links), role names typed by a person in the Cockpit.
- Backend summary (#634): `construct summarize --backend [<dir>] [--format json]` reads a Node.js / Express backend and reports, read-only, with no model and no rules: the route map (method, full path with `use('/prefix', router)` mounts resolved across files through variables, imports, `require`, router factories such as `createNotesRouter({...})`, chained `router.route('/x').get(...).post(...)`, array and constant paths and registrars such as `mountRoutes(app)`; handler file and function name, own and inherited middleware by registration order and path, `file:line`), each file's role (`route`, `store`, `service`, `auth`, `job`, `util`, `config`, `test`, `other`, with the reason for each, overridable through a `backend:` section of `architecture.yml`, which also takes `dir`), the import graph with named cycles, `process.env` names (never values) and effects (fs, child_process, network, timers) with `file:line`. A plain `http.createServer` handler is read only for `req.url === '/x'` conditions; anything it cannot read (a computed path, a mount that is not a visible router) is listed as "not detected", never guessed. `--format json` prints `backend-summary.v1` (`schemas/backend-summary.v1.json`, bounded, project-relative paths); the MCP `summarize` tool takes an optional `backend: true`. Dogfooded on `ui/server/src`: 122 of 122 route registrations and 50 of 50 `use()` registrations found, none missed or invented, one loop-registered route reported once as computed; about 10 of 63 role verdicts arguable and none forced an override. Left out: Fastify, Koa, Nest, rules, a `framework` option, a Cockpit screen, a plan flow. Express and plain Node servers only. See docs/BACKEND-SUMMARY.md.

## [0.9.0] - 2026-09-24

The MVP release: a five-screen Cockpit with durable Notes, a calmer interface, blocks you can see and switch off, a workspace of your own on a hosted Cockpit, and results you can trust on a real project. Package versions are `0.9.0`; the Cockpit (`ui/`) is not versioned separately yet.

### Added
- `TYPE-001` (off by default, opt-in via `rules: { TYPE-001: error }` in `architecture.yml`): `construct validate` runs the project's own TypeScript (`tsc --noEmit -p tsconfig.json`) and reports each diagnostic as a violation with its `TSxxxx` code, file and line; if TypeScript or the tsconfig is missing it warns `TYPE-001 could not run: <reason>` instead of passing silently ([#495]). A solution-style root tsconfig (`references`, no `files`/`include`, as in a Vite/React template) is now expanded: each referenced project is checked with `tsc --noEmit -p` (never `tsc -b`) and the diagnostics merged; a missing reference or a config that resolves to zero files warns `TYPE-001 could not run: ...` instead of passing, and the checked configs are reported as `typeCheck.checked` ([#579]).
- Cockpit: interactive commands (`/api/create`, `/api/import`, ...) are queued per signed-in login instead of one server-wide queue, so one user's long command no longer delays another's; `CONSTRUCT_MAX_CONCURRENT_COMMANDS` (default 2) caps how many run at once across all users. Each command's console output and exit code are captured per command (`setExitCode`/`withExitCodeSink` in `packages/core/diagnostics.mjs`; core commands no longer write `process.exitCode` directly), so concurrent commands never see each other's output or status ([#569]).
- `defineService(name, fn, { schema })`: an optional response schema, checked at the service's boundary. `schema` is any Standard Schema object (`~standard.validate` — zod 3.24+/4, Valibot, ArkType, or hand-written) or a `safeParse`-shaped one; core imports no schema library. The unit then returns `{ status: 'ok', value }` (typed as the schema's output) or `{ status: 'error', kind: 'schema', issues }` — never a throw — keeping `fn`'s own sync/async-ness; the two-argument form is unchanged ([#585], part of [#575]).
- Cockpit shell: five screens (Features, Pages, Components, Git, Tests) in a left rail, a profile menu (Settings, Local model, Theme, Help, Sign out), and the whole UI blocked until a project is open. Features, Pages and Components browse in the left pane and open in the stage; the Pages screen can show the real app full screen and at device sizes ([#243], [#368], [#369], [#370], [#429], [#431], [#456]).
- Durable Notes: a per-project draft that autosaves 800 ms after you stop typing, survives a reload and a server restart, and offers Keep mine / Load theirs / Compare when another tab saved first. The Plan screen writes its own note: `?note=<id>` follows it, step edits save the plan, editing the text afterwards shows "Plan out of date" (Keep this plan), and Run marks the note ran and keeps it as read-only history (editing it starts a copy). "Ticket" is now "Notes" everywhere users read ([#366], [#373], [#561], [#609]).
- Open a project: clone from GitHub, and a New project action that creates an initialised folder in your workspace ([#330], [#445], [#562]).
- A workspace of your own on a hosted Cockpit: DevOps sets the root (`CONSTRUCT_WORKSPACE_ROOT`), each signed-in user is confined to `<root>/<login>/`, the project picker lists only your projects, and project state is per session so two users can be signed in at once ([#566], [#567], [#568], [#569]).
- Blocks: a uniform block contract (`packages/core/block-contract.mjs`, `block-flows.mjs`, `docs/BLOCK-CONTRACT.md`) with an audit of every plan flow; a Blocks tab in the Features Browser pane lists each block in plain words and lets you turn it off per project or set its default engine. A turned-off block is refused server-side (`COCKPIT_BLOCK_DISABLED`) on every screen that starts it, and nothing starts ([#407], [#543], [#563], [#611]).
- A plan built in the Cockpit declares the files its steps write (`packages/core/plan-touches.mjs` derives them for `create.feature`, `create.unit` and `create.layer`, pinned against the real generators), so the approval gate can approve them one by one; the step card shows "writes <file>" ([#470], [#564]).
- The Cockpit and the CLI give the same result: the per-project execution mode now covers summarize, doctor, review, create, refactor and import as well as validate, each with an engine/CLI byte-identical contract test ([#560]).
- Workflows: `WORKFLOW-004` transition-table completeness and an opt-in typed state union with an exhaustive matcher for generated workflows ([#571], [#572], [#578], [#580]).
- Logos as status lights: the Cockpit logo moves only while the framework is working (a command, the Import Wizard, a Process) and the tab icon flips with it; the docs logo is a status light too, driven by `GET /api/dev-status` (public, booleans only, read from local agent activity, off unless enabled), with its mode and a Logo Lab motion set in `site/logo.json` or in your own browser ([#614]).
- Brand marks (Line, Construct, Cockpit, CLI), a login hero, a reusable animated loader, and a calmer login screen ([#401], [#406], [#424], [#455]).
- Components screen: props read with react-docgen ([#434]). API reference for every package, versioned with the documentation site ([#463], [#464], [#465], [#466], [#467], [#468]).

### Changed
- A calmer Cockpit: Settings drops the "Current resolution" panel, the Dashboard opens with Create and folds Refactor, Research and Import under "More actions", Help opens only "Getting started", the status bar shows one "? Shortcuts", buttons say what they do ("Create feature", "Check impact"), plain words replace derived/inferred ("Computed"/"Guess"), and empty states end with one primary action ([#391], [#565]).
